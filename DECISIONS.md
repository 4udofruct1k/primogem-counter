# DECISIONS.md

Мелкие технические решения, которые спека оставляет на усмотрение разработчика (правило 6).
Формат: номер · этап · решение · почему.

## M0 — монорепо

**D-001 · M0 · TypeScript 6.0, а не 7.0.**
`typescript-eslint` 8.x поддерживает `typescript < 6.1`. TS 7 (нативный компилятор) пока несовместим с линтером.
В TS 6 `types` по умолчанию пустой — каждый пакет перечисляет нужные типы явно (`node`, `vite/client`).

**D-002 · M0 · Версии инструментов.**
Vite 8, `@vitejs/plugin-react` 6, Vitest 5, React 19, Fastify 5, ESLint 10 (flat config), Prettier 3, zod 4, Node ≥ 22.12
(минимум для Vite 8). Версии закреплены точно в `package.json`, lockfile в git.

**D-003 · M0 · Внутренние пакеты подключаются исходниками.**
`@primo/domain` и `@primo/shared` экспортируют `./src/index.ts` без отдельной сборки. Vite и tsx понимают TS напрямую;
прод-сборка `api` будет бандлить их (решение о бандлере — на этапе M3/M10).

**D-004 · M0 · Один запуск тестов на весь репозиторий.**
Корневой `vitest.config.ts` с `test.projects` (`packages/*`, `apps/*`); `pnpm test` = `vitest run` по всем проектам.
У каждого пакета свой конфиг с `name`, тесты лежат рядом с кодом (`*.test.ts`).

**D-005 · M0 · `pnpm dev`.**
`pnpm --parallel --filter @primo/api --filter @primo/web dev`: api — `tsx watch` на :3000, web — Vite на :5173 с прокси
`/api` и `/data` на :3000 (15.7). Отдельный `concurrently` не нужен.

**D-006 · M0 · Линтер следит за чистотой `domain`.**
В `packages/domain` ESLint запрещает импорты React / Fastify / Dexie / Zustand и глобалы `fetch`, `window`, `document`,
`localStorage`, `indexedDB` — ядро остаётся чистыми функциями (раздел 2, правило 3).

**D-007 · M0 · Сборочные скрипты зависимостей.**
pnpm 10 по умолчанию не запускает postinstall; разрешённые пакеты перечислены в `onlyBuiltDependencies`
(`pnpm-workspace.yaml`). Сейчас там `esbuild`; нативные модули (argon2) добавятся на M3.

**D-008 · M0 · `/api/health` до подключения БД.**
До M3 отвечает `{ ok: true, db: "unconfigured", version }`. На M3 поле `db` станет реальной проверкой (`up` / `down`).

**D-009 · M0 · Postgres для разработки слушает только 127.0.0.1.**
`deploy/compose.dev.yml` публикует порт как `127.0.0.1:5432`, чтобы dev-БД с паролем `primo` не была видна в сети.

## M1 — domain

Решения D-101, D-102, D-104 приняты пользователем (вопросы при старте M1).

**D-101 · M1 · Недоступное «по расписанию», но ещё доступное — в прогнозе.** _(решение пользователя)_
Баланс меняется только после отметки «забрал». Прогноз = накопленное + всё, что ещё можно получить сейчас и в будущем:
planned-вхождение с невышедшим дедлайном попадает в прогноз в момент `max(expectedClaimAt, now)`.
Это расширяет формулу 8.1 (`now < expectedClaimAt ≤ T`), из-за которой незабранные письма к годовщине, текущая бездна
или HoYoLAB месяца выпадали из прогноза до самого дедлайна. Функции `isClaimableBy` / `claimAt` в `recurrence.ts`.

**D-102 · M1 · Компенсации за обновление — 600 за версию.** _(решение пользователя, сверено с патчноутами)_
300 за техработы (почтой в течение 5 ч после обновления, письмо живёт 30 дней) + 300 за исправления (нужно войти
в течение ~3 дней). Ивент датапака `<версия>-maint-comp` — это то же письмо за техработы, поэтому для такой версии
вхождение `maint_comp:<версия>` не генерируется. Связь — соглашение по id, `data/*.json` не меняется.

**D-103 · M1 · `events_tpl` отменяют только ивенты без метки `leak`.**
7.4 содержит лишь утёкший «Праздник морских фонарей» (primo: null, 10 IF) — шаблон 1790 для 7.4 остаётся, иначе
«Ожидаемо» теряло бы ивенты версии из-за одной утечки. Примогемы фонарей null, поэтому двойного счёта нет.

**D-104 · M1 · Магазин пыли — настройка «N IF и M AF в месяц», по умолчанию 0.** _(решение пользователя)_
Баланс пыли и её пополнение не моделируются, `stardustByBalance` (8.3) не используется. Вхождение
`stardust_shop:<YYYY-MM>` получает награду из настройки (не больше 5 + 5 из датапака, метка `user`); фактическую
покупку месяца человек отмечает сам. TC-12 переформулирован: «настройка 2 IF, 0 AF → 2 IF в месяц, AF 0».

**D-105 · M1 · Пробные персонажи (perPhase).**
Баннер с `phase: null` относится к фазе 1. Фаза без известных баннеров персонажей → награда `null` (метка
`unknown`, блок «не учтено»), а не выдуманные 2 × 20. Метка = самая слабая из правила и баннеров (7.3 → `leak`).

**D-106 · M1 · Горизонт «now − 1 версия» = now − 42 дня** (длина версии по 4.3), вперёд — now + 400 дней.

**D-107 · M1 · Ивент без даты окончания** (`end: null`) — дедлайн = «дедлайн конца версии» его версии,
задержка забора 168 ч. Иначе такие ивенты висели бы в прогнозе бесконечно.

**D-108 · M1 · Проекции версий.** Id растут по минорной части (7.5 → 7.6 → …). `durationDaysOverride` сдвигает
последующие `projected` версии (и с датой из пака), но не версии с официальной датой.

**D-109 · M1 · Коды стрима**: если у версии есть `specialProgram` — вхождение начинается в эту дату, иначе старт − 12 дней.

**D-110 · M1 · Метаданные правил.** У правил датапака нет `title` / `category` — они берутся из `catalog.ts`
(названия раздела 6, категории типа `Category`). `enabled` по умолчанию true. Правило без `windowDays` и
`deadlineAnchor` (`maint_comp`) действует до конца версии (раздел 6).

**D-111 · M1 · Задания ивента — отдельные вхождения** `<eventId>:<taskId>`: письма и миссии отмечаются по одному.
При наличии `tasks` общая `reward` ивента не суммируется повторно.

**D-112 · M1 · Флаги — наложение при расчёте.** «Сундуки 100%», «Область закрыта», «Регион закрыт» не меняют
документы `CategoryProgress`, а перекрывают их в `effectiveProgress` / `collected`. Снятие флага возвращает ручной
прогресс автоматически (I9), `flagSnapshot` не нужен (поле оставлено в типе для совместимости схемы).

**D-113 · M1 · Id категорий.** `<areaId>:<kind>`, повтор `kind` в области — `_2`, `_3` в порядке seed
(`sumeru_main:offering_2`). Общие источники — `general:<id>`; их план хранится в `AreaState` с этим id.

**D-114 · M1 · `count` без единицы и `checklist` без единицы.** Бездна 1–8: единица = ⌊итог / число⌋ = 300 (как в 11.5),
при полном счётчике собрано = итог (2405). Чек-лист без `unit` — итог / число пунктов.

**D-115 · M1 · Пороги HoYoLAB 4 / 11 / 18 × 20** в seed есть только текстом (`endgame.hoyolab.rule`), поэтому
продублированы константой; тест сверяет её с текстом правила и `maxPerMonth`.

**D-116 · M1 · Метки в сценариях.** `announced` входит во все сценарии (раздел 0: Минимум исключает только projected,
leak, unknown). `unknown` проходит везде: null → 0 и строка в «не учтено» (I5). Метка вхождения — метка суммы
правила, а не проекция даты версии (8.2: «метки сумм»).

**D-117 · M1 · Платное в «Минимуме» — только купленное**: луна — реальные покупки (без виртуальных `keepActive`),
БП — только уже начавшиеся версии, плановые пополнения не учитываются.

**D-118 · M1 · Трекеры в прогнозе.** В прогноз идёт `ожидание сценария − уже начисленная сумма трекера` (не меньше 0).
Режимы ожидания: `pack` (из датапака, по умолчанию) / `max` / `last` / `avg3` / ручное; `expectedMin`: `pack` / `min3` /
ручное. У натиска нет `expectedMin` в паке — берётся `expected`.

**D-119 · M1 · Луна.** +300 crystal — вхождение `welkin:<purchaseId>:buy`. Покупка, после которой у луны было бы
больше 180 дней, отклоняется. `keepActive` — виртуальные покупки `v<YYYY-MM-DD>` в последний день активной луны
(или сегодня, если луны нет).

**D-120 · M1 · Разовый контент в прогнозе (11.6).** «Ожидаемо»: `byDate` — в дату плана, `rate` — недельными порциями
(начисление в конце недели или в момент, когда область закончилась). «Максимум»: весь остаток областей с планом —
сразу. Область будущей версии (`addedIn`) — не раньше старта этой версии. Категории `leak` — только в «Максимуме».

**D-121 · M1 · Id записей леджера**: `claim:<occId>:<at>`, `unclaim:<occId>:<at>` — запись только добавляется,
повторная отметка после отмены не конфликтует с первой.

**D-122 · M1 · Формат времени** — канонический `YYYY-MM-DDTHH:mm:ssZ`; Luxon с фиксированными смещениями.
Тип `Version` дополнен вычисленными `bpEnd`, `bpPurchaseEnd`, `endDeadline`, `generated`; `Occurrence` —
`title`, `category`, `paid`, `tracker`, `virtual`, `expectedMin`.
