# DECISIONS.M3.md

Фрагмент для DECISIONS.md — решения этапа M3 (api). Формат тот же: номер · этап · решение · почему.

## M3 — api

**D-301 · M3 · Postgres в тестах API — PGlite.**
Docker-демона в окружении нет, поэтому `testcontainers` (15.7) недоступен; `pg-mem` — эмулятор без `citext` и
`SELECT … FOR UPDATE`. PGlite 0.5 — настоящий PostgreSQL (WASM) в процессе, с `contrib/citext`; тесты гоняют те же
SQL-миграции, что и прод. Приложение не зависит от драйвера: `buildApp({ config, db })`, где `db` — drizzle
`PgDatabase`; прод и `pnpm dev` — node-postgres по `DATABASE_URL`, тесты — `drizzle-orm/pglite`.
`DATABASE_URL=pglite:memory` или `pglite:<папка>` — запуск без Docker для разработки (PGlite — dev-зависимость,
грузится лениво). PGlite собран из PG 18 — миграции используют только возможности PG 16.

**D-302 · M3 · Миграции.** drizzle-kit в `apps/api/drizzle/`: `0000_citext` — ручная
(`CREATE EXTENSION IF NOT EXISTS citext`; расширение доверенное, суперпользователь не нужен), `0001_init` — из
`src/db/schema.ts`. Применяются при старте сервера (drizzle migrator). Папка — `../drizzle` от `src/` или `dist/`,
либо `MIGRATIONS_DIR`. Новые миграции: `pnpm --filter @primo/api db:generate`.

**D-303 · M3 · Сессии.** Cookie `sid` — 256-битный токен (base64url); в `sessions.id` хранится его SHA-256, чтобы
утечка таблицы не давала войти. Срок `SESSION_TTL_DAYS` (30); когда осталось меньше половины — продление на полный
срок и новая cookie. Истёкшая сессия удаляется при обращении и при следующем входе пользователя. `Secure` по
умолчанию только в production (`COOKIE_SECURE` переопределяет), `Path=/`.

**D-304 · M3 · Лимиты и CSRF.** `@fastify/rate-limit`, счётчики в памяти (api — одна копия). Вход, восстановление и
всё, что проверяет пароль (смена пароля, новый код, удаление аккаунта): 5 в минуту на IP и 10 в час на логин, счётчики
общие; считаются все попытки. Регистрация — 10 в час на IP (argon2id на 64 MiB дорог). Готовые хуки плагина на один
маршрут ставят только один лимит (общий флаг «уже проверено»), поэтому — `createRateLimit` и своя цепочка в preHandler.
IP клиента — `trustProxy`: верим X-Forwarded-For только от loopback и частных адресов (Caddy в docker-сети,
`TRUST_PROXY`). Origin: `PUBLIC_ORIGIN` (список) и `https://$DOMAIN`, вне production ещё Vite `:5173`; нет Origin или
чужой → 403 FORBIDDEN (браузеры шлют Origin на любой POST/PUT/DELETE).

**D-305 · M3 · Sync: отклонения по документу.** Запрос не по `SyncRequestSchema` (коллекция, > 500 изменений) →
400 VALIDATION целиком. Документ не по схеме своей коллекции (`parseDoc`) и удаление из `ledger` / `wallet_snapshot`
не сохраняются и возвращаются в новом поле ответа `rejected: [{ collection, id, message }]`; остальные изменения
запроса применяются — один битый документ не блокирует очередь. Хранится документ после zod (лишние поля отброшены).

**D-306 · M3 · Sync: версии и курсор.** Одна транзакция на запрос; первым — `SELECT … FOR UPDATE` строки `users`:
записи одного пользователя идут по очереди, и клиент не проскочит курсором чужую незакоммиченную запись с меньшим seq.
Нет документа на сервере = `{ data: null, version: 0, deleted: true }`: правка с `baseVersion > 0` — конфликт;
удаление документа, которого не было (создан и удалён офлайн), — запись-надгробие version 1. Append-only: существующий
id → в `applied` с текущими version и seq без изменений, `baseVersion` не проверяется. Ответ — до 1000 изменений по
seq, дальше `more: true` и курсор = последний отданный seq, иначе курсор = max seq пользователя. Курсор больше max seq
(БД восстановлена из бэкапа) → отдаём всё с нуля.

**D-307 · M3 · Аккаунт.** Код восстановления — 16 символов из A–Z и 2–9 без 0/O/1/I/L (~79 бит), argon2id-хэш.
`recover` выдаёт новый код и закрывает все сессии (клиент затем сам вызывает `login`). Смена пароля закрывает
остальные сессии, текущая остаётся. Новый код — `POST /api/auth/recovery-code { password }`. Неверный текущий пароль —
401 BAD_CREDENTIALS. Неизвестный логин сверяется с фиктивным хэшем — время ответа не выдаёт, есть ли логин.
Регистрация отвечает 201. argon2id в проде — m 64 MiB, t 3, p 1, через env не меняется; облегчённые параметры только
в объекте `Config` тестов. Одновременно считается не больше `UV_THREADPOOL_SIZE` (4) хэшей — до 256 МБ памяти.

**D-308 · M3 · Игровые данные и админка.** Манифест собирается на лету: датапак — самый новый
`data/datapack-*.json` по имени; SHA-256 файлов кэшируется по mtime и размеру (правка файла видна без перезапуска);
`Cache-Control: no-cache`. Статика `data/*.json` (только `.json`) — `public, max-age=300`: файлы с датой в имени
тоже правятся на месте (D-125). Патчи админки — таблица `admin_patches` (version pk, jsonb, `created_by` → users,
on delete set null); каждое сохранение — новая версия, старые не меняются. `/data/patch-<n>.json` отдаётся из БД с
`immutable`, хэш в манифесте — от той же JSON-строки. PUT: схема патча → `applyDatapackPatch` → `DatapackSchema`
итога → `baseVersion` = последней версии, иначе 409 (гонку двух сохранений ловит первичный ключ → тоже 409).
Админы — флаг `users.is_admin` от оператора (D-316; прежде — `ADMIN_USERNAMES`). Для M10: Caddyfile из 15.3
раздаёт `/data/*` сам с диска, а манифест и патчи теперь живут в api — `/data/*` нужно проксировать в api (или хотя
бы `manifest.json` и `patch-*.json`).

**D-309 · M3 · Прод-сборка.** tsup → ESM `dist/server.js`; `@primo/domain`, `@primo/shared` (и luxon) внутри бандла,
npm-зависимости api — снаружи (образу нужен `node_modules` с prod-зависимостями api; argon2 — готовый нативный
бинарник), PGlite — отдельный ленивый чанк. `start` = `node dist/server.js`; пути по умолчанию считаются от
`import.meta.dirname` (`src/` и `dist/` на одном уровне). SIGTERM/SIGINT — корректная остановка с закрытием пула.
`@node-rs/argon2` ставится готовым бинарником платформы без postinstall — `onlyBuiltDependencies` (D-007) не меняется.

**D-310 · M3 · Ошибки и логи.** Ошибки Fastify (413 — тело больше 1 МБ, 415, битый JSON) → код VALIDATION с исходным
статусом; любой неизвестный путь → 404 NOT_FOUND; прочее → 500 INTERNAL с записью в лог. Логи — JSON (pino), redact:
cookie, set-cookie, тела запросов, поля `password`, `newPassword`, `currentPassword`, `recoveryCode`.

**D-311 · M3 · Дополнения к API 14.4.** `GET /api/docs/:collection/:id` — свой неудалённый документ или 404;
`POST /api/auth/recovery-code`; `GET` / `PUT /api/admin/patch`; `/api/me` отдаёт `isAdmin`. `/api/health` при
недоступной БД — 503 `{ ok: false, db: "down" }` (закрывает D-008).

**D-312 · M3 · Предел документа и квоты аккаунта.** Документ — не больше 256 КБ (`DOC_MAX_BYTES` в shared): размер —
байты UTF-8 `JSON.stringify` документа после схемы коллекции (`jsonBytes`), так он уходит по сети. Больший — в
`rejected` («Документ 301 КБ — больше предела 256 КБ, сервер его не сохранил»), остальные изменения применяются
(D-305). Настоящие документы — единицы КБ; чек-лист `cat_progress` с `flagSnapshot` на пределах схемы (200 отметок
по 300 символов) — ~120 КБ. Свободные поля схем ограничены: `sim_preset` и `user_entity.data` — 16 КБ JSON (форма «Молитв» ~1 КБ,
своя область или категория — сотни байт), `override.value` — 4 КБ (имя, цена, флаг), строки-идентификаторы
(`goal.target.bannerId`, `chestLog.type`, ключи записей) — 200 символов, `cat_progress.updatedAt` — 64. Квоты
аккаунта — `USER_MAX_DOCS` (по умолчанию 200 000 строк, включая удалённые: надгробие тоже строка) и `USER_MAX_MB`
(32 МБ суммы размеров). Оценка: активный игрок за день — до ~20 записей леджера, ~10 статусов вхождений и 2–3
снимка кошелька, это ~33 строки и ~5 КБ, за год ~12 000 строк и ~2 МБ — квот хватает на 16 лет такого темпа.
Изменение, которое добавило бы строку или байты сверх квоты, — в `rejected` («Лимит аккаунта — не больше 32 МБ
данных: изменение не сохранено»); правки, уменьшающие размер, и удаления проходят всегда, даже сверх квоты (если её
уменьшили). Счётчики — `users.doc_count` / `doc_bytes`, меняются только в /api/sync под блокировкой строки
пользователя (O(1), а не сумма по таблице на каждый запрос); размер строки — `user_docs.size` (у удалённой 0).
Миграция `0002_sync_limits` заполняет их по `octet_length(data::text)` — с пробелами jsonb это чуть больше
`JSON.stringify`, квота считается с запасом. Худший случай на диске — ~32 МБ данных и ~200 000 строк по ~250 байт,
около 80 МБ на аккаунт плюс дампы; от множества аккаунтов — лимит регистрации (D-304).

**D-313 · M3 · Ответы /api/sync и экспорт ограничены по байтам.** Страница `changes`: до 1000 строк (D-306), и строка
входит, только если данных до неё меньше 1 МБ (`syncPullMaxBytes`); первая — всегда, курсор движется и при документе
больше бюджета. Отбор — в SQL: оконная сумма `size` по seq под `LIMIT`, лишние строки до Node не доходят; `more` —
последний отданный seq меньше max seq пользователя. Данные конфликтов — в том же бюджете: если следующий конфликт его
превысит (первый — всегда), сервер прекращает обработку запроса; оставшиеся изменения не попадают ни в `applied`, ни в
`conflicts`, ни в `rejected`, ответ — `more: true`, клиент шлёт их снова (веб снимает запись очереди только по ответу
о ней). Существующие документы для проверок читаются без `data`. Итого ответ — до ~2 МБ плюс два документа.
`GET /api/export` — поток (`Transfer-Encoding: chunked`), а не одна строка в памяти: страницы по (collection, doc_id)
с продолжением от последнего ключа, до 500 строк и 1 МБ; в памяти — одна страница, соединение пула между страницами
не держится. Квота (D-312) ограничивает и объём экспорта, но память от неё не зависит. Первая страница читается до
начала ответа — ошибка БД там даёт обычный ответ-ошибку, позже — обрыв ответа. Экспорт — не единый снимок:
документ, изменённый во время экспорта, попадёт в старом или новом виде, но один раз.

**D-314 · M3 · Один /api/sync пользователя за раз, частота записей, тайм-ауты.** В процессе (api — одна копия,
D-304) не больше одного /api/sync и одного экспорта на пользователя: второй сразу получает 429 RATE_LIMIT с
`Retry-After: 1`, не открывая транзакцию и не занимая соединение пула (раньше каждый параллельный sync держал одно из
10 соединений в ожидании `FOR UPDATE` строки пользователя, и десяток запросов одного аккаунта останавливал весь
сервер). До проверки — только `authenticate`, один короткий запрос. /api/sync с изменениями — не больше 60 в минуту на
пользователя со всех устройств (`createRateLimit` по id): ограничивает поток записей при заполненной квоте; чтение без
изменений не считается. Предохранители: у пула `connectionTimeoutMillis` 5 с (дальше 500, а не бесконечная очередь),
в транзакции sync — `lock_timeout` 5 с и `statement_timeout` 15 с (`set_config(…, true)`); тайм-аут блокировки →
429 RATE_LIMIT «Данные аккаунта заняты другой операцией». 429 — ближайший код из 14.4: клиенту нужно повторить позже.

**D-315 · M3 · Эпоха данных сервера: восстановление из бэкапа (15.5) не прячет изменения от курсоров.**
`pg_restore --clean` возвращает `user_docs_seq` к значению из дампа, и новые записи получают seq, которые клиенты уже
прошли курсором; ветка D-306 «курсор больше max seq» ловит это, только пока после восстановления записано мало.
Эпоха — 16 hex от md5(`system_identifier` из `pg_control_system()` и OID последовательности `user_docs_seq`):
`pg_restore --clean` удаляет и заново создаёт последовательность (новый OID), восстановление в новый кластер меняет
`system_identifier`, перезапуски api и Postgres её не меняют. Хранить нечего: эпохи нет в дампе, `backup.sh` и
команда 15.5 прежние, восстановление ловится и на работающем api (эпоха читается в каждой транзакции sync) и для
дампов любого возраста. Вариант со случайной эпохой в UNLOGGED-таблице отвергнут: он зависит от
`pg_dump --no-unlogged-table-data` (ручной дамп без флага вернул бы старую эпоху), не замечает восстановления дампа,
снятого до появления таблицы, и сбрасывается после аварийного перезапуска Postgres. Протокол: ответ /api/sync всегда
несёт `epoch`, запрос может нести `epoch` из последнего применённого ответа. Не совпала — сервер игнорирует курсор
(всё с seq 0, дальше страницами по `more`) и считает конфликтом любую правку с `baseVersion > 0`: версии до
восстановления несравнимы, совпавший номер может быть другим состоянием; новые документы (`baseVersion` 0) и «только
добавление» — как обычно. Нет `epoch` в запросе — прежнее поведение. Не ловится только восстановление без
пересоздания последовательности (`pg_restore --data-only`, ручной `setval` назад). Перенос базы через dump/restore
(например, на новую мажорную версию Postgres) тоже сменит эпоху — клиенты один раз скачают всё заново.

**D-316 · M3 · Админ данных — флаг аккаунта от оператора, а не логин.** `ADMIN_USERNAMES` давал права любому, кто
зарегистрирует логин из списка: до регистрации оператора (новый сайт виден в CT-логах с выпуска сертификата) и снова —
после удаления аккаунта админа, а патч админа применяют все клиенты (14.6). Теперь права — `users.is_admin`
(миграция `0003_admin_flag`, по умолчанию false); ставит и снимает их только оператор командой сервера
`node dist/cli.js admin grant|revoke <логин>`, список — `admin list` (tsup собирает `dist/cli.js` рядом с
`dist/server.js`; в проде — `docker compose -f compose.prod.yml exec api …`, `DATABASE_URL` уже в окружении
контейнера; код выхода 0, 1 — нет аккаунта или ошибка БД, 2 — неверный вызов). У API пути к флагу нет. Флаг живёт в
строке аккаунта: удаление аккаунта уносит его, новый владелец того же логина — обычный пользователь; `grant` меняет
строку по id и печатает id и дату регистрации — оператор сверяет, что аккаунт его. Флаг читается вместе с сессией в
каждом запросе: `revoke` действует сразу, без выхода. `/api/me.isAdmin` — тот же флаг, контракт прежний.
`ADMIN_USERNAMES` удалена, а не оставлена как начальная выдача: выдача по имени при старте гоняется с регистрацией
(имя, занятое до перезапуска, получит права), а выдача без гонки — создать аккаунт с паролем из env — держала бы пароль
админа в `.env`. Заданная переменная — предупреждение в логе при старте api: иначе админ после обновления молча
потерял бы доступ. Резервировать имена при регистрации незачем — имя прав не даёт. CLI миграции не применяет: их
применяет api при старте, а мигратор drizzle работает без блокировки (два одновременных запуска применяют одну
миграцию дважды); на старой схеме CLI просит запустить api этой версии. Дамп старше `0003_admin_flag` после
восстановления и перезапуска api админов не содержит — права выдаются заново.
